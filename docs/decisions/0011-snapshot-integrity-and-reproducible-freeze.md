# 0011 - Assessed snapshot integrity and reproducible freeze protocol

**Status:** Proposed (accepted only after implementation and verification; the acceptance commit records the date and time)

**Date:** 2026-11-22

**Related:** decisions 0009 and 0010; GitHub issues #8 and #15.

**Scope:** CP3 model selection, final fitting and the single held-out evaluation.

## Context

The assessed data are stored in `snapshots/assessed_snapshot.db`. `snapshots/MANIFEST.json` records the snapshot creation time, row counts, the raw-response hash check and the SHA-256 hashes of the snapshot files. Decision 0010 records the snapshot SHA-256 `9ff58bb40ffc09ed2a7ff929d7a2f6ecce85b12b9c5bcdf55ef427ae1693d6c2`.

The selection pipeline (`analysis/selection.py`, commit `11dec23`) records the hash of the database when a path is supplied and hashes the Python files in `analysis/`. It does not yet verify the database against the manifest or against the hash fixed in decision 0010, record the Git revision or working-tree state, hash all files it depends on, or enforce the pinned package versions. The analysis code imports `monitoring/coverage.py` and `monitoring/prepare.py`, which the current manifest does not hash.

This decision is recorded before the first assessed-snapshot selection run. It changes no candidate, fold, cut-off, criterion or tie-break rule of decisions 0009 and 0010.

## Decision

Before the first assessed-snapshot selection run, the following safeguards must be implemented and tested.

### 1. Snapshot integrity

The selection process must:

- require `snapshots/assessed_snapshot.db` and `snapshots/MANIFEST.json` to exist;
- calculate the SHA-256 of the database and compare it with both (a) the `assessed_snapshot.db` entry of `MANIFEST.json` and (b) the expected value fixed in the code as a constant, equal to the hash recorded in decision 0010;
- stop with a clear error if any of the three values differ. A manifest edited together with the snapshot must not pass;
- record the SHA-256 of the database and of `MANIFEST.json` in the selection manifest;
- open the database read-only and never modify it.

The raw-response hash check and row counts in `MANIFEST.json` remain provenance evidence.

### 2. Code, configuration and environment provenance

The selection manifest records, for each of the following files, the SHA-256 of the file bytes and its Git blob hash:

- every `analysis/*.py` file;
- `monitoring/coverage.py` and `monitoring/prepare.py`;
- `requirements.txt`, `pyproject.toml` and `pytest.ini`;
- `docs/decisions/0009-late-model-freeze.md`, `docs/decisions/0010-analysis-implementation-choices.md` and this decision;
- any other file the selection pipeline imports or reads.

Line endings: the repository stores text files with LF. A `.gitattributes` file containing `* text=auto eol=lf` and `*.db binary` must be committed before the freeze because `.gitattributes` is not on the post-freeze allow-list (section 8). The Git blob hash is the cross-platform reference; the byte hash is recorded as supporting evidence.

Environment: the manifest records the Python, NumPy, pandas, scikit-learn, matplotlib, pytest and setuptools versions. Selection stops if the installed NumPy or scikit-learn version differs from the pin in `requirements.txt` (decision 0010, item 29 relies on this). A different Python version is recorded, not blocked.

Git blob hashes are obtained from the committed Git objects corresponding to the recorded HEAD. The clean-working-tree check in section 3 ensures that the tracked working files match that committed revision.

### 3. Git provenance and working-tree integrity

Before selection starts, the pipeline must:

- record the Git HEAD commit, its tree hash and the branch name;
- perform the clean-working-tree and remote-containment checks before creating the new run directory. Outputs generated by the current run must not be treated as pre-run working-tree changes;
- verify that the working tree is clean and stop if tracked or untracked changes are present. Files ignored by `.gitignore` are not counted;
- fetch the latest `main` from `origin` into the `origin/main` remote-tracking reference before checking remote containment;
- if the fetch succeeds, verify that HEAD is contained in the fetched `origin/main` and stop if it is not;
- if the remote cannot be reached or checked, record a warning in the selection manifest and do not claim that the remote check passed;
- record the start time of the run in UTC and in Asia/Tashkent time, for the actual-times table of decision 0009.

The selection run must be associated with a committed and identifiable version of the project.

### 4. Development-only selection

- The existing receipt-time and valid-time cut-offs remain mandatory.
- The held-out test period must not be loaded, inspected or used.
- The expanding-window folds and the candidate and tie-break rules of decisions 0009 and 0010 are unchanged.
- The outputs record the selected configurations, fold-level results, aggregate metrics and the provenance information above.

### 5. Separate selection run directories

Selection is one recorded event under decision 0009. Every run writes to its own numbered directory. No run may overwrite, delete or modify the outputs of an earlier run.

The directory structure is:

```text
results/selection/
    run-001/
        cv_table.csv
        selected_configurations.json
        selection_manifest.json
    run-002/
        cv_table.csv
        selected_configurations.json
        selection_manifest.json
```

The rules are:

- `--out` specifies the base directory, defaulting to `results/selection`. It does not specify an individual run directory.
- The script creates the numbered run directory itself. The next run number is one greater than the highest existing numeric `run-*` directory. For example, if `run-001` and `run-003` exist, the next directory is `run-004`.
- The run directory is created with `exist_ok=False`. If the target directory already exists, the script stops and never reuses it.
- The directory is created when a run starts. `selection_manifest.json` is written last, after the run outputs and their hashes have been produced.
- A run directory without a manifest is an incomplete run. Its number remains used and must never be reused.
- If any `run-*` directory already exists, another selection run requires both `--rerun` and a non-empty `--reason`. Otherwise, selection stops.
- A rerun manifest records `previous_run` and `rerun_reason`. `previous_run` identifies the most recent earlier completed run, if one exists. If no earlier run completed, it is recorded as `null`.
- Each additional run is recorded in decision 0009. Earlier run directories are never modified.
- The clean-working-tree rule in section 3 also applies. Outputs from a completed run must be committed before another run can start.
- The freeze manifest explicitly identifies the selection run it uses through `selection_run` and records the SHA-256 hashes of that run's three output files.
- The freeze must use the latest numbered run, and that run must be complete. If the latest numbered run is incomplete, the freeze stops until the incomplete attempt is resolved and documented. The freeze must not silently fall back to an earlier run.
- The run chosen for the freeze is determined by run order, not by cross-validation performance. The report discloses all selection runs and their results.

### 6. Conditions for the selection run

The assessed-snapshot selection is run only after:

1. the safeguards in sections 1 to 5 are implemented and tested with synthetic data;
2. the selection, final-fit and evaluation code and their synthetic regression tests are committed (decision 0010, item 16);
3. `.gitattributes` is committed;
4. the working tree is clean and HEAD is pushed.

The remaining post-test code (Q1 to Q4 inference, exploratory analysis, error analysis, bootstrap, leave-one-city-out and sensitivity analyses) must be committed and tested before the freeze tag, not necessarily before the selection run.

The code hashes in the freeze manifest for `analysis/selection.py`, `analysis/modelling.py`, `analysis/data.py`, `analysis/cutoffs.py`, `monitoring/coverage.py` and `monitoring/prepare.py` must equal those in the manifest of the run named in the freeze manifest. If any of them changed between the selection run and the freeze, the freeze is refused and the cause is recorded in a decision.

### 7. Freeze

After selection, the selected configurations, final-fit artefacts, preprocessing state, CV table and SHA-256 manifest are committed in one commit. This commit is tagged with the annotated tag `late-freeze-YYYYMMDD-HHMM` (decision 0010, item 16).

The freeze manifest identifies the exact selection run used and contains the required hashes. The held-out evaluation is run only after the annotated freeze tag exists.

### 8. Post-freeze restriction

After the `late-freeze` tag, commits may change only `results/`, `docs/`, `README.md` and `.gitignore`.

- There are no exceptions. The evaluation guard to be implemented under decision 0010 must enforce this restriction automatically and require exactly one `late-freeze-*` tag. If a change to frozen code is unavoidable, the freeze is declared invalid in a new decision and the consequences are reported.
- The commit-diff check applies to the first evaluation. No code, including CP4 dashboard or API code, may be committed between the tag and the first evaluation.
- Later runs with `--post-test` verify the frozen configuration and model-artefact hashes against the freeze manifest and label all output as post-test work.
- All evaluation, inference, error-analysis, bootstrap, leave-one-city-out and sensitivity code must therefore exist, with synthetic tests, before the tag.

## Acceptance tests (synthetic data only)

- A snapshot whose bytes differ from the manifest or from the fixed constant stops selection. A manifest changed together with the snapshot also stops it.
- A missing snapshot or manifest stops selection.
- A modified tracked file and an untracked file each stop selection in a temporary Git repository; ignored files do not.
- The selection manifest contains the hashes, versions, HEAD, tree hash, branch and run times listed above.
- A NumPy or scikit-learn version differing from the pin stops selection.
- The first run writes `run-001/`.
- A second run without both `--rerun` and `--reason` stops. With both arguments, it writes `run-002/`, leaves `run-001/` byte-identical and records the reason and `previous_run`.
- A run directory without a manifest counts as a used number. The next run requires `--rerun --reason` and writes the next unused number.
- If existing run numbers contain gaps, the next run uses the number after the highest existing number rather than reusing a gap.
- The script never writes into an existing run directory.
- The freeze manifest names the exact run directory and records the hashes of its three output files.
- With multiple runs, the latest numbered run must be complete before the freeze can proceed. The freeze uses that run, not the run with the best cross-validation result.
- The snapshot file is byte-identical before and after selection.

## Consequences

The assessed data, project code, dependencies, Git revision, selection outputs and freeze are linked by verifiable hashes and metadata. Selection may stop when the snapshot, working tree or provenance information is incomplete or inconsistent; this is intentional. The separation between development-only model selection and the single held-out evaluation becomes explicit and checkable.
